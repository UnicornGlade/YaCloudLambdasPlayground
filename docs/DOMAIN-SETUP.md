- приватный служебный бакет для Terraform state с версионированием. State сертификата/DNS и bootstrap перенесён туда, блокировка проверена конкурентным тестом.

**Владелец уже сменил NS в Руцентре.** Новые NS и CNAME подтверждены через Google DNS-over-HTTPS. Сертификат пока остаётся `VALIDATING`: его проверка может занимать от часов до дней. Приложение без БД уже развёрнуто на техническом адресе API Gateway; PostgreSQL ещё не создан. См. [CLOUD-STAGE1.md](CLOUD-STAGE1.md).

## Что нажать в Руцентре

Проверено по скриншотам владельца: сейчас включена услуга **«Статусная страница»**, а не DNS-хостинг с редактором записей. Предыдущая инструкция о ручном добавлении CNAME в кабинете Руцентра больше не нужна.

1. **Личный кабинет → Домены → unicornglade.tech**.
2. В строке **«DNS-серверы»** нажать **«Изменить»** (не «Дочерние DNS-серверы»).
3. В разделе **«Сторонние DNS»** выбрать **«Указать DNS-серверы самостоятельно»**.
4. Указать по одному имени в поле:

   ```text
   ns1.yandexcloud.net
   ns2.yandexcloud.net
   ```

5. В итоговом списке оставить **только эти два сервера**. Старые `statuspage1.nic.ru` / `statuspage2.nic.ru` или `ns*.nic.ru` не добавлять рядом с ними.
6. Нажать **«Сохранить изменения»** и подтвердить действие, если кабинет спросит.
7. Сообщить агенту, что изменения сохранены.

Имена вводятся без `https://`, IP-адресов и путей. Не нужно покупать DNS-хостинг Руцентра, переносить регистрацию домена или менять записи DNSSEC. Если форма отличается или просит обязательные дополнительные параметры — показать скриншот до сохранения.

Эти NS не угаданы: они получены из созданной зоны через `yc dns zone list-records`.

## Проверка после смены NS

```bash
npm run certificate -- nameservers  # ожидаемые NS из Cloud DNS
npm run certificate -- dns          # ожидаемая CNAME-запись
npm run certificate -- status       # свежий статус сертификата

dig +short NS unicornglade.tech
dig +short CNAME _acme-challenge.playground.unicornglade.tech
```

Нужно увидеть новые NS, правильную CNAME и затем статус сертификата `ISSUED`. Это разные этапы; сохранение формы ещё не доказывает, что все кеши обновились.

Распространение изменений обычно занимает от минут до нескольких часов, иногда до 24–48 часов. Не следует многократно переключать NS туда-сюда во время ожидания.

В текущем окружении прямые `dig @авторитетный-сервер` возвращали рекурсивные ответы без флага AA, поэтому нельзя выдавать их за независимую проверку авторитетных серверов. Для дополнительной проверки используем DNS-over-HTTPS (например, Google Public DNS) и read-only API Certificate Manager. DNS-зона и её записи проверены через API Yandex Cloud; новые публичные NS и CNAME теперь также подтверждены через Google DNS-over-HTTPS.

## Будущая почта Яндекс 360

Почта будет вида `name@unicornglade.tech`, независимо от сайта на поддомене. При подключении Яндекс 360 добавим в ту же зону:

- запись подтверждения владения доменом;
- MX;
- SPF (не создавать несколько отдельных SPF-записей);
- DKIM с данными из кабинета Яндекс 360;
- DMARC с согласованной политикой.

Значения заранее не выдумываем. Существующий TXT GlobalSign сохраняем. Яндекс 360 оплачивается отдельно от DNS и облачной инфраструктуры сайта.

## Стоимость и инфраструктура

DNS-зона: `0,0592 ₽ × 720 часов = 42,624 ₽` за 30 дней, плюс `37,94 ₽ / миллион` авторитетных запросов (около 1,90 ₽ за 50 тысяч). Цены для России с НДС. Certificate Manager отдельно не тарифицируется. Служебный state занимает килобайты; для него действуют обычные тарифы/бесплатные лимиты Object Storage.

Terraform DNS и сертификата остаётся в `infra/certificate/` (историческое имя директории), служебный бакет — в `infra/bootstrap/`. Доступ: краткоживущая сессия `yc`, эфемерный S3-ключ на один час, ограниченный служебным бакетом. Постоянные ключи не создавались.
