# PostgreSQL: согласованный план и расчёт стоимости

План подтверждён владельцем и применён. Кластер создан, миграции выполнены, сейчас STOPPED между занятиями. Фактические проверки и ограничения описаны в [DATABASE-STATUS.md](DATABASE-STATUS.md). Ниже сохранён первоначальный расчёт и план.

## Почему пересчитана стоимость

Предыдущий ориентир использовал `c4a-c2-m4`. В нашем облаке `yc managed-postgresql resource-preset get c4a-c2-m4` вернул NotFound, а list не содержит этот класс. Хотя он описан в документации, создавать его без проверки доступности нельзя.

`b1`/`b2` по-прежнему могут появляться в API, но документация запрещает создание новых кластеров этих классов. `c3-c2-m4` относится к Compute Optimized: доступ по запросу, а стоимость выше стандартного `s3-c2-m8`.

Предлагается один хост **s3-c2-m8**, Intel Ice Lake, 2 × 100% vCPU, 8 ГБ RAM, 10 ГБ network-ssd, без реплик и публичного IP. Этот preset возвращается API, в том числе для `ru-central1-d`. Это не гарантия наличия физических ресурсов в момент создания.

## Стоимость

Россия, RUB с НДС, 30 дней = 720 часов:

- Вычисления: `2 × 1,8792 + 8 × 0,5072 = 7,816 ₽/час` работы.
- SSD: `10 × 0,0218 × 720 = 156,96 ₽/30 дней`, включая периоды остановки.

| Режим БД за 30 дней | Вычисления + диск |
|---|---:|
| Всё время остановлена | 156,96 ₽ |
| Работает 50 часов | 547,76 ₽ |
| Работает 100 часов | 938,56 ₽ |
| Работает 720 часов | 5 784,48 ₽ |

Не включены существующий DNS (~43 ₽/30 дней плюс запросы), дополнительные услуги Lockbox, превышение бесплатных квот serverless/логов/трафика и резервные копии сверх включённого объёма. Резервные копии в пределах суммарного дискового пространства кластера не тарифицируются отдельно. Остановка именно network-ssd кластера освобождает вычислительные ресурсы; с local-ssd экономия была бы другой.

Рекомендуемый режим — учебный, с остановкой между занятиями. Автоматическая остановка пока НЕ настроена. После создания БД продолжает оплачиваться до фактической остановки; настройка `PRODUCTION` означает окружение сервиса, а не круглосуточное расписание.

## Что подготовлено в Terraform

`infra/database/`, отдельный backend `terraform/database.tfstate`. `init`, `validate` и `plan` выполнены. План: **11 создать, 0 изменить, 0 удалить**:

- одна VPC;
- пять подсетей — по одной в зонах `a`, `b`, `d`, `e`, `k`, которые API Compute на момент проверки возвращает как UP (зона `c` — DOWN);
- security group для PostgreSQL;
- один кластер PostgreSQL 17 в зоне `d`;
- два пользователя: `counter_owner` для миграций и `counter_app` для приложения;
- одна база `counter`.

Требование подсетей во всех зонах взято из документации Cloud Functions. План подтверждает корректность схемы Terraform, но не доказывает возможность создания каждой подсети: перед apply нужно повторно сверить доступность зон. Не переключать зоны/класс на более дорогие варианты автоматически при ошибке.

Важные настройки:

- Публичный IP выключен. Входящий TCP/6432 разрешён с `198.19.0.0/16` — служебных подсетей Cloud Functions в подключённой VPC, а не с произвольных адресов интернета. Отдельно разрешено внутреннее взаимодействие членов SG.
- Функции не имеют собственного настраиваемого SG в этой схеме; правило разрешает соединения функций, подключённых к данной VPC. Не считать его идентификацией конкретной функции — дополнительно нужны отдельные DB-пользователи и секреты.
- Резервные копии сохраняются 7 дней. `deletion_protection` и Terraform `prevent_destroy` включены.
- Пароли не задаются в HCL/переменных: `generate_password=true`, Connection Manager должен сгенерировать их на стороне сервиса и хранить в Lockbox. Не добавлять Terraform data source, читающий содержимое этих секретов в state.
- DB-пользователь приложения не является владельцем базы. SQL-права SELECT/UPDATE на счётчик нужно выдать отдельным шагом после миграции.
- SESSION pooling выбран для корректной работы существующих session advisory locks мигратора.
- Флаг `access.serverless=false` отключает отдельный механизм подключений через сервисную интеграцию. Планируем обычное сетевое TLS-подключение из VPC.

Обновление после apply: VPC, четыре доступные подсети a/b/d/e, БД и пользователи созданы; секреты сгенерированы сервером, функции подключены к VPC, миграции выполнены. Подсеть k создать не разрешено; несозданный ресурс исключён из конфигурации. Инкремент и полный HTTPS smoke пока не подтверждены. Первоначальный plan сам по себе не являлся проверкой PostgreSQL.

## Барьер перед платным apply

Обёртка запрещает случайное `npm run infra -- database apply` без явного флага. После подтверждения владельцем нового класса и стоимости:

```bash
npm run infra -- database plan
# Проверить свежий план и только затем:
npm run infra -- database apply --approve-database-cost
```

Не обходить это прямым Terraform apply. Сохранённый бинарный план находится в `.tools/database.tfplan`, не в Git.

## Первоначальная последовательность после согласования (актуальные результаты — DATABASE-STATUS.md)

1. Создать ресурсы; при ошибке исправлять без destroy и удаления данных.
2. Получить только metadata созданных Connection Manager/Lockbox ресурсов, назначить раздельные права runtime и мигратору.
3. Передавать секреты функции через Lockbox, не печатать пароль/URL в терминал и не публиковать их. Собрать DATABASE_URL только на сервере либо безопасно подготовить отдельный секрет.
4. Добавить CA Yandex в серверный артефакт, включить TLS verify-full, использовать master FQDN и порт 6432.
5. Создать отдельную приватную функцию миграций, доступную только авторизованному оператору, без публичного HTTP-маршрута. Подключить её к VPC и выполнить миграции от counter_owner.
6. Выдать counter_app только нужные SQL-права, подключить приложение, проверить readiness и один явно разрешённый инкремент.
7. Реализовать start/stop с явным выбором правильного кластера и проверить сохранность значения после остановки/старта.
8. После этого — релизы, откат и архив, без изменения применённых миграций и сброса счётчика.
