# Terraform: DNS, сертификат и безопасный state

## Что реализовано

- Terraform 1.16.2 в `.tools/terraform/`, установщик проверяет закреплённый SHA-256 официального дистрибутива (linux/amd64).
- Провайдер `yandex-cloud/yandex` 0.228.0, lock-файлы в Git.
- `infra/bootstrap/`: приватный бакет `unicornglade-tfstate-b1gh1fk7hbuj5hu9tujb`.
- `infra/certificate/`: существующий сертификат, публичная зона `unicornglade.tech.` и DNS-записи.
- Оба state перенесены из local backend в S3. Старые локальные `.tfstate.backup` — только резервные копии, не актуальный источник состояния; не публиковать и не загружать поверх актуального state.

`infra/application/` теперь описывает запуск приложения без БД: бакет сайта, функцию, API Gateway, IAM, scaling policy и логи. State — `terraform/application.tfstate`. Реальная проверка и публикация описаны в [CLOUD-STAGE1.md](CLOUD-STAGE1.md). Managed PostgreSQL, VPC для него и бакет архивов ещё не созданы.

## Авторизация

Войти через актуальный CLI (`yc init --username='<почта Яндекс ID>'`), выбрать `lambda-playground-folder`. Скрипты проверяют cloud/folder и отказываются работать в другом каталоге.

Для провайдера IAM-токен передаётся только через окружение дочернего процесса. Для S3 backend создаётся эфемерный ключ с жизнью один час и политикой `infra/backend-access-policy.json`. Он ограничен нужным бакетом и объектами `terraform/*`; в файлы, аргументы Terraform и вывод команд ключ не записывается. Отладочное логирование Terraform отключается. Не запускать эти операции с shell tracing и не публиковать окружение процессов.

В CLI 1.34.0 `--policy` принимает JSON-текст; передача пути к файлу приводила к выдаче ключа с некорректной политикой. Скрипт читает только несекретный файл политики и передаёт его содержимое. Для session policy Yandex также требует явный Principal.

Начальная bucket policy допускает только уже авторизованного владельца `ajev28h57merhi7r168p`. Для другого оператора или CI необходимо отдельно согласовать сервисный аккаунт и расширение доступа; не заменять Principal на `*` ради устранения ошибки.

## Команды

```bash
npm run tools:terraform
npm run infra -- bootstrap init
npm run infra -- certificate init
npm run infra -- bootstrap validate
npm run infra -- certificate validate

npm run infra -- bootstrap plan
npm run infra -- certificate plan
# После проверки сохранённого плана:
npm run infra -- bootstrap apply
npm run infra -- certificate apply

npm run certificate -- nameservers
npm run certificate -- dns
npm run certificate -- status
```

Планы сохраняются в `.tools/bootstrap.tfplan` и `.tools/certificate.tfplan` с правами 0600. Apply применяет только ранее созданный план, не формирует и не одобряет новый автоматически. Секреты не передаются через `-backend-config` или переменные HCL.

Алиас `npm run certificate -- init|validate|plan|apply` работает с тем же модулем, включая DNS. В нём больше не только сертификат.

## Хранилище state

- `terraform/bootstrap.tfstate` — бакет state.
- `terraform/domain.tfstate` — DNS и сертификат.
- `terraform/application.tfstate` — приложение без БД.
- `terraform/lock-probe.tfstate` — небольшой синтетический тест блокировки без ресурсов приложения.

Бакет закрыт для анонимного чтения, списка и конфигурации. Проверен HTTP 403 на анонимный HEAD реального state. Versioning включён, наличие `version_id` подтверждено через HEAD metadata без чтения тела state. Политика запрещает HTTP и разрешает HTTPS только конкретному владельцу. Terraform `prevent_destroy` и `force_destroy=false` защищают от случайного удаления через этот код.

Используется native S3 locking `use_lockfile=true`, без дополнительной БД. Проверено на реальном backend:

```bash
node scripts/check-state-lock.mjs
```

Тест использует отдельный state, встроенный `terraform_data` и локальный `sleep`. Пока один процесс держит `.tflock`, конкурентный plan отклоняется; после завершения блокировка штатно снимается. Не запускает destroy инфраструктуры и не меняет счётчик. Тест пишет только свои state/lock-объекты в приватный бакет.

После первого создания бакета возникла ошибка 403: в отличие от привычной AWS-схемы, политика Yandex с одним Deny блокировала также владельца. Исправлено добавлением Allow конкретному владельцу, без публичного доступа. Версионирование завершено через management API, существующий бакет не пересоздавался, Terraform затем показал отсутствие изменений. В зафиксированной конфигурации корректная политика уже присутствует.

Провайдер выдаёт предупреждения о deprecated inline ACL/policy; выбранная закреплённая версия их поддерживает, итоговый plan сходится без изменений. Отдельные ресурсы ACL/policy можно внедрить позднее с аккуратной миграцией владения, не снимая защиту бакета.

## Bootstrap и восстановление

Первый бакет был создан с временным local backend. После создания и проверки бакета оба модуля переключены на S3, затем выполнены:

```bash
npm run infra -- bootstrap migrate
npm run infra -- certificate migrate
```

Эта одноразовая операция копирует state средствами Terraform, не печатая его содержимое. **Не повторять миграцию или apply старого локального state без проверки актуального backend.**

При обычном клонировании репозитория на другую машину бакет уже существует: достаточно браузерной авторизации и `init`. Секреты/state не нужно получать из Git.

Если потребуется развернуть совершенно новое облако, сначала нужен новый согласованный bootstrap с local backend, новыми идентификаторами и именем бакета; затем миграция в S3. Нельзя просто направить существующий код на чужое облако. Если state утрачен, восстанавливать его из версий S3 или импортировать существующие ресурсы, а не удалять и пересоздавать их.

Перед добавлением секретов PostgreSQL в state отдельно согласовать права сервисных аккаунтов и требования к шифрованию/резервному копированию. `sensitive=true` скрывает значения в обычном плане, но не удаляет их из state.
