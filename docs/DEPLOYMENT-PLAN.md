# План первого облачного деплоя

## Решения

- Один репозиторий, Nuxt + Nitro с пресетом `aws_lambda`.
- Один хост Managed PostgreSQL без реплик, ориентир `c4a-c2-m4`, 10 ГБ `network-ssd`. Проверить доступность класса в выбранной зоне.
- Один бакет сайта, отдельный бакет больших файлов, отдельное приватное служебное хранилище state/артефактов.
- Веб-страница и `/api/*` через один API Gateway. Большие файлы — напрямую из Object Storage.
- Предлагаемый адрес: `playground.unicornglade.tech`, **ожидает подтверждения**. Корневую A-запись не менять.
- Существующие NS у регистратора сохраняются. Первоначальные DNS-записи добавляются владельцем, если нет согласованной автоматизации DNS.
- Никаких Kubernetes, постоянно работающего веб-сервера или CDN на старте.
- Инфраструктура описывается Terraform. Сборка и загрузка файлов — отдельные операции внутри одной команды деплоя, а не отдельный Terraform resource для каждого JS-файла.

Ориентир расходов при малой нагрузке: около 4 400 ₽ за 30 дней постоянной работы или 500–800 ₽ при 50–100 часах работы БД. Это оценка, не лимит. Трафик архивов и превышение бесплатных квот оплачиваются отдельно.

## Этап 1 — приложение без облачных изменений

- [x] Nuxt-страница, API, миграция.
- [x] Проверка типов и unit-тесты.
- [x] Два артефакта: статический сайт и серверный ZIP.
- [x] Локальный вызов настоящей Lambda-сборки в изоляции от node_modules репозитория.
- [ ] Интеграционный тест с настоящим PostgreSQL: нужен локальный сервер БД.

## Этап 2 — доступ, выбор каталога и Terraform

- [ ] Владелец обновляет авторизацию через `yc init`; секреты остаются в локальной конфигурации.
- [ ] Проверить cloud, folder, платежный аккаунт и доступные квоты. Желательно выделить отдельный каталог проекта, не использовать чужие ресурсы.
- [ ] Подтвердить доменное имя и первоначальный режим работы БД (постоянный или учебный с остановкой).
- [ ] Установить закреплённую версию Terraform с проверкой контрольной суммы. Закрепить провайдер в `.terraform.lock.hcl`.
- [ ] Реализовать bootstrap приватного backend state, ограничить права, включить versioning и проверить способ блокировки state. Не хранить state в публичном бакете или Git.
- [ ] Разделить права управления инфраструктурой, публикации артефактов и чтения диагностики.
- [ ] Для секретов использовать Lockbox, учесть попадание некоторых значений в Terraform state даже при sensitive=true.
- [ ] Перед первым созданием платных ресурсов показать `terraform plan` и обновлённую оценку расходов.

## Этап 3 — минимальный облачный вызов и HTTPS

Сначала проверить Cloud Functions без БД, чтобы не оплачивать PostgreSQL во время решения вопросов DNS/совместимости.

- [ ] Создать приватную Cloud Function с обёрткой `index.handler`, выбрать поддерживаемую среду Node.js, согласованную с engines Nuxt.
- [ ] API Gateway вызывает функцию от собственного сервисного аккаунта с `payload_format_version: '2.0'`.
- [ ] Опубликовать артефакты и проверить `/api/health` на техническом HTTPS-домене.
- [ ] Certificate Manager: managed-сертификат на подтверждённый поддомен с DNS-проверкой.
- [ ] Вывести владельцу точные имя/значение записи проверки сертификата из Terraform, а не угадывать их.
- [ ] После выпуска сертификата привязать домен к API Gateway, добавить CNAME поддомена на выданный шлюзом адрес. Проверить DNS и HTTPS снаружи.
- [ ] Не переносить всю DNS-зону и не менять корневые A/MX/TXT-записи без отдельного согласования.

## Этап 4 — БД и полный сценарий

- [ ] VPC и необходимые подсети во всех зонах согласно требованиям Cloud Functions.
- [ ] Managed PostgreSQL без публичного IP; ограниченные сетевые правила для доступа функций.
- [ ] Один хост на сетевом SSD, резервные копии, защита от случайного удаления.
- [ ] Приложение подключается к актуальному основному серверу по специальному FQDN с проверкой TLS.
- [ ] Приватный механизм запуска миграций внутри VPC: не открывать БД в интернет и не добавлять публичный `/api/migrate`.
- [ ] По возможности раздельные пользователи БД для миграций и приложения: приложению не нужны DDL-права.
- [ ] Ограничить масштабирование функции, время выполнения и частоту запросов через шлюз.
- [ ] Настроить JSON-логи и получение логов из CLI, по request ID/периоду/версии. Проверить интеграцию Monium: Cloud Logging объявлен к закрытию во II квартале 2027 года.
- [ ] Бюджетные уведомления, ограниченное хранение логов, очистка старых артефактов/версий секретов.
- [ ] Небольшой тестовый ZIP (около 1 ГБ или меньше) в отдельном бакете; проверка HEAD и пробное скачивание с согласованным размером.

## Этап 5 — удобство релизов и приёмка

Предлагаемый интерфейс (**команды ниже, кроме smoke, ещё не реализованы**):

```text
npm run deploy         # сборка → миграции → публикация → smoke
npm run logs           # диагностика; только чтение
npm run status         # адреса, версии, состояние БД
npm run infra:start    # запустить БД и дождаться готовности
npm run infra:stop     # остановить БД, не удаляя данные
npm run rollback       # вернуть совместимый релиз приложения
```

- [ ] Один способ владения версиями функции: CLI и Terraform не должны взаимно откатывать изменения (избежать configuration drift).
- [ ] Идентифицировать релизы, сохранить манифест соответствия сайта и серверной версии.
- [ ] Новый JS/CSS загружается до переключения HTML. Старые хешированные файлы не удаляются сразу.
- [ ] API должен быть совместим со старым фронтендом в момент релиза. Обновление двух сервисов не атомарно.
- [ ] Откат приложения не откатывает автоматически данные/миграции БД; разрушительные миграции требуют отдельного плана.
- [ ] Обычный релиз не пересоздаёт БД, сеть или большие файлы.

Приёмочный сценарий:

1. Развернуть v1, открыть страницу по HTTPS, увеличить счётчик.
2. Проверить в другом браузере, что значение общее.
3. Задеплоить v2 одной командой, проверить новую версию и сохранность счётчика.
4. В контролируемом эксперименте получить ошибку, найти её логи по request ID.
5. Откатить приложение, снова проверить данные.
6. Проверить скачивание архива напрямую из отдельного бакета.
7. Проверить start/stop БД: при остановке статика и архив остаются доступны, API счётчика возвращает ошибку; после запуска данные сохраняются.
8. Только после этого по желанию временно добавить реплики и проверить переключение основного сервера.
