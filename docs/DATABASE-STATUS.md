## Результат

После подтверждения владельцем класса и стоимости создан PostgreSQL `playground-postgresql`, ID `c9q1pfg88e94keapkuue`: один `s3-c2-m8`, 10 ГБ network-ssd, PostgreSQL 17, без публичного IP. Финальный статус **STOPPED**. Вычисления не оплачиваются во время остановки; диск остаётся платным (~156,96 ₽/30 дней), другие услуги оплачиваются отдельно.

Созданы VPC и четыре подсети a/b/d/e. Зона k возвращалась API как UP, но создание подсети запрещено нашему каталогу. Исключена только несозданная подсеть, существующие ресурсы не удалялись. Повторный database plan показал No changes.

## Что проверено, а что нет

Подтверждено реальными облачными вызовами:

- приватная функция миграций применила `001-counter.sql`, значение `0`;
- приложение с отдельным DB-пользователем прочитало счётчик через Cloud Function: HTTP-совместимый ответ 200, `{"value":"0"}`;
- stop → start действительно выполнены; после старта приложение прочитало прежнее значение `0`;
- повторная миграция вернула `applied: []`, значение осталось `0`;
- сделана первая ручная резервная копия (около 3,3 МБ, DONE); без неё сервис отказался останавливать новый кластер;
- после проверок БД снова остановлена, статус STOPPED подтверждён.

**НЕ подтверждено:** успешный POST-инкремент и полный end-to-end smoke через публичный API Gateway с подключённой БД. HTTPS-запросы из текущего окружения завершались TLS EOF/ECONNRESET/handshake timeout, иногда также к Functions и management API. Причина сетевых сбоев не установлена. Успешный IAM-вызов функции нельзя выдавать за успешный запрос через публичный шлюз.

После неуспешного POST не выполнялся слепой автоматический повтор: сначала проверялось фактическое значение. Финальный повторный мигратор прочитал `0`, успешный инкремент не зафиксирован. При следующем занятии начать с чтения и полного smoke, а затем выполнить один явный инкремент.

Локально прошли typecheck, 16 unit-тестов и 5 тестов артефактов Lambda/мигратора. Отдельный localhost DB integration test не запускался — облачные проверки не заменяют этот тест.

## Секреты и подключение

Connection Manager сгенерировал пароли на стороне облака. Содержимое Lockbox не выгружалось в терминал, чат, Git или Terraform variables/state. Использованы только metadata: ID секрета, ID версии и имя ключа `postgresql_password`.

- `counter_app`: отдельный сервисный аккаунт `playground-runtime`, право payloadViewer только на секрет приложения.
- `counter_owner`: отдельный `playground-migrator`, право payloadViewer только на секрет владельца БД.
- Cloud Functions внедряет пароль в серверную переменную `PGPASSWORD`. `PGHOST`, `PGUSER`, `PGDATABASE`, `PGPORT` — несекретные настройки; URL собирается только внутри серверного `databaseConfig` с экранированием пароля.
- TLS: `verify-full`, `rejectUnauthorized=true`, CA Yandex включён только в серверные ZIP. Хост: `c-c9q1pfg88e94keapkuue.rw.mdb.yandexcloud.net`, порт 6432.
- CA скачан по HTTPS с https://storage.yandexcloud.net/cloud-certs/CA.pem; SHA-256: `6d148f85b5213445b23ad22ff45e47e1aa2be968f183f9bd6ff39de54d47a8ef`.
- Пользователь приложения получил USAGE схемы, SELECT/UPDATE таблицы global_counter, но не CREATE/DDL и не пароль владельца.
- Версии секретов закреплены в `infra/application/database.tf`. При ротации обновлять metadata и версию функции, не читать payload в Terraform.

## Приватные миграции

`playground-migrate` (`d4envfjsgvfmbg9ee0ni`) — отдельная Cloud Function с IAM-доступом. В спецификации шлюза маршрута к ней нет. Она принимает только `{"action":"migrate"}`, не принимает произвольный SQL/пути. Обёртка команды проверяет результат `status=ok`, а не только exit code CLI.

Сборка создаёт `.artifacts/migration.zip` из существующего мигратора и неизменённых SQL-файлов. Внутри ZIP зависимости находятся в `runtime/node_modules`: первая попытка с корневым node_modules столкнулась с удалением зависимости pg при облачной сборке. Исправлено без переустановки/удаления БД; добавлен тест загрузки пакета в изоляции с отсутствующим корневым node_modules.

## Команды

```bash
npm run database:cloud -- status
npm run database:cloud -- start       # возобновляет оплату вычислений
npm run database:cloud -- migrate     # приватный IAM-вызов, повторяемые миграции
npm run smoke -- https://playground.unicornglade.tech
npm run smoke -- https://playground.unicornglade.tech --increment  # один явный POST
npm run database:cloud -- stop        # данные остаются, диск оплачивается
```

Первая остановка нового кластера требует резервную копию. Для этого есть `npm run database:cloud -- backup` (кластер должен работать). Для текущего кластера первая копия уже создана.

Скрипт проверяет cloud/folder, ID, имя и состояние именно нашего кластера; нет destroy, удаления данных или автоматического повторения операций. При таймауте сначала проверить status, не предполагать, что операция не произошла. Start/stop меняет вычисленное состояние кластера, не его Terraform-конфигурацию.

**Автоматического расписания остановки нет.** После своего занятия нужно явно выполнить stop. Пока БД остановлена, счётчик недоступен; при исправном HTTPS статика и liveness /api/health от БД не зависят.

## Деплой

```bash
npm run check
npm run infra -- application plan
# Просмотреть план, затем:
npm run infra -- application apply
npm run database:cloud -- migrate
npm run publish:site
npm run smoke -- https://playground.unicornglade.tech
```

БД должна быть запущена. План защищён хешем обоих ZIP и release.json; не пересобирать артефакты между plan/apply. На первом внедрении мигратора серверная версия была опубликована до начальной миграции; далее API и миграции должны оставаться совместимыми при неатомарном обновлении.

В этой сессии один зависший план был прерван внешним таймаутом, оставив S3 lock. После проверки отсутствия Terraform-процесса снята только собственная блокировка OperationTypePlan. Это не инструкция применять force-unlock при любых ошибках: сначала доказать, что блокировка не принадлежит работающему оператору.
