# Правила работы с проектом

## Фактический статус

Сначала читать `README.md` и `docs/DEPLOYMENT-PLAN.md`, для DNS также `docs/DOMAIN-SETUP.md`, для Terraform — `docs/TERRAFORM.md`. Первый облачный запуск без БД выполнен: статика, приватная Cloud Function и API Gateway проверены по техническому HTTPS-адресу, логи реально прочитаны. См. `docs/CLOUD-STAGE1.md`. DNS уже делегирован, но сертификат ещё VALIDATING и собственный домен не подключён. PostgreSQL не создан. Локальный Lambda-тест сам по себе по-прежнему не доказывает работу облака.

## Проверки

- `npm ci` — воспроизводимая установка.
- `npm run check` — типы, unit-тесты, сборка, локальные тесты Lambda.
- `npm run test:db` без TEST_DATABASE_URL пропускает тест. Пропуск не является проверкой PostgreSQL.
- Интеграционный тест разрешён только с отдельным localhost PostgreSQL и явным TEST_DATABASE_URL.
- `npm run smoke -- <url>` по умолчанию read-only. `--increment` действительно меняет глобальный счётчик и требует соответствующего намерения пользователя. `--without-db` проверяет этап без БД с ожидаемым 503 readiness, не является проверкой PostgreSQL и несовместим с `--increment`.

## Безопасность

- Не читать и не печатать OAuth/IAM-токены, `.env`, `~/.config/yandex-cloud/config.yaml` или Terraform state целиком.
- Для проверки yc использовать команды получения конкретных несекретных параметров или read-only API. При истёкшей сессии попросить владельца войти через браузер с актуальным CLI (`yc init --username=...`); не просить прислать токен в чат. Для Terraform IAM-токен передаётся только в окружении дочернего процесса, без вывода и записи в HCL.
- Подтверждены playground.unicornglade.tech и перенос DNS всего unicornglade.tech в Yandex Cloud. Владелец уже заменил NS на ns1.yandexcloud.net/ns2.yandexcloud.net; внешний DNS подтверждён. Корневую A-запись 178.210.92.188, A для www и TXT GlobalSign сохранить; новые изменения этих записей — отдельно согласовать. Яндекс 360 пока только план, не создавать MX/SPF/DKIM наугад.
- State bootstrap, сертификата/DNS и приложения уже в приватном S3 backend с versioning и use_lockfile. Не возвращаться к local backend и не затирать актуальный state старыми локальными резервными копиями. Читать только конкретные публичные outputs или metadata, не state целиком. Использовать обёртки с эфемерными ключами, не создавать постоянные административные ключи.
- Перед первым созданием платных ресурсов показать план и стоимость. Не выполнять destroy или удаление данных ради устранения ошибки деплоя.
- Не выполнять административные изменения Docker/прав сокета без согласования. Особенно не делать сокет доступным всем.
- Не запускать миграции из публичного HTTP endpoint.
- Не менять применённые SQL-миграции. Не сбрасывать счётчик при релизе.
- В публичный бакет загружать только `.artifacts/site`, никогда не репозиторий целиком.

## Архитектура

- Nuxt 4, ssr=false, явный пререндер `/`, Nitro preset aws_lambda, без response streaming.
- API Gateway payload_format_version=2.0; обёртка deploy/function/index.js копируется в CommonJS-пакет.
- Backend и frontend — отдельные артефакты одной сборки.
- DATABASE_URL только на сервере; проверять TLS в облаке, не использовать rejectUnauthorized=false.
- Счётчик BIGINT передаётся строкой. Инкремент одним UPDATE ... RETURNING, без read-modify-write и автоматических повторов POST.
- Пул PostgreSQL ограничен. Функция ограничена одним экземпляром и запросом на зону, timeout 10 секунд; это не глобальный лимит расходов. Rate limit/WAF и бюджетные уведомления ещё нужны.
- Версиями функции и тегом live управляет только Terraform. Не пересобирать ZIP между plan и apply. Статику публиковать через `npm run publish:site`, index.html последним, без удаления старых assets.
- `cloud:status` и `cloud:logs` — read-only диагностика без чтения state. Логи ограничены 15 минутами/30 записями/64 КБ. Не заменять это неограниченной выгрузкой или постоянными административными ключами.
